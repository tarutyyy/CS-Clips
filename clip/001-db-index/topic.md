# インデックスはなぜ速い？
## 伝えたい一点
インデックス（B+木）は 1 つのノードに目印を数百個持つので木が浅く、1 億行でも数段たどるだけで目的の行に着く。

## 想定視聴者・前提知識
SQL で SELECT / WHERE を書いたことがある人。木構造の知識は不要。

## 使いたい見せ方のアイデア
- 行のグリッドを先頭から順に光らせ、カウンターが 1 億に向かって回る（全件走査）
- そのグリッドが木に変形する（場面を切らず、同じ画面の中で）
- 根 → 内部ノード → 葉 と、たどる道筋だけが順に光り、カウンターは 4 で止まる

## 触れないこと（スコープ外）
- ノード分割・再バランス、書き込みコスト、複合インデックス、ハッシュ索引
- B 木と B+木の厳密な違い（動画では「B+木」と呼ぶ）

## 選ばなかった論点
- 書き込みが遅くなる代償（別クリップ向き）

## Gate1 自己判定
- 伝えたい一点は 1 つ：はい
- 60 秒で伝えきれる大きさ：はい
- 動きで見せる価値（全件走査 → 木の変形 → 道筋）：はい
