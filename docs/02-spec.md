# CS-Clip 仕様書

外から見た振る舞い（制作手順・ファイル形式・コマンド・出力品質）を定める。内部構造は設計書に書く。

## 1. 用語
| 用語 | 意味 |
|---|---|
| クリップ | 動画 1 本の単位。`clip/NNN-slug/`（ID はディレクトリ名） |
| パート | クリップを役割で分けた単位（前提・本編・まとめ、総集編ではつなぎ）。台本・音声・映像がパートの中で閉じる（04 契約書 §2.2） |
| ビート | ナレーション 1 文と、それに対応するアニメーション 1 動作の組。パートに属する |
| タイミング | 各ビートの開始フレーム・長さ。TTS の結果から自動算出される。パートの頭を 0 として数える |
| ゴール | 見終わった人が言えるようになる一文。台本はここに向かって進む（§3.1） |
| 核・支え | 台本の文の重要度。核＝ゴールそのもの、支え＝核を理解するのに要る事実（§3.3） |
| 学習メモ | オーナーが書いた Markdown。システムへの入力。`clip/NNN-slug/memo.md` として置く |
| ゲート | 人間がレビューして承認する関門（Gate1〜3）。レビューモードのときだけ止まる |

## 2. 制作ワークフロー
入口は `/make-video <クリップのパス> [--review]`（例：`/make-video clip/001-db-index`）の 1 つ。事前にオーナーが `clip/NNN-slug/memo.md` を置いておく。Claude Code が以下を順に実行する。

| # | ステップ | 担当 | 入力 → 出力 | ゲート（`--review` 時のみ停止） |
|---|---|---|---|---|
| 0 | 準備 | Claude | `clip/NNN-slug/memo.md` → `clip.yaml`（id・題名・分野・kit・parts を生成） | |
| 1 | 論点の設計 | Claude | memo.md → `topic.md`（生まれた理由・ゴール・要点の地図・見せ方・選ばなかった論点） | **Gate1 論点** |
| 2 | 裏取り | Claude | topic.md + memo.md → `research.md`（生まれた理由も裏取りする） | |
| 3 | 台本 | Claude | topic.md + research.md → `script.md`（パートごと、文に重要度の印） | **Gate2 台本** |
| 4 | ビート分割 | Claude | script.md → パートごとの `beats.yaml` | |
| 5 | 音声生成 | コマンド | beats.yaml → パートごとの `audio/`, `timing.json` | |
| 6 | 映像実装 | Claude | beats.yaml + timing.json → パートごとの `Scene.tsx` | |
| 7 | 自己検証 | Claude | 主要フレームの静止画を見て、6 に戻って直す（最大 3 回） | |
| 8 | 検証・書き出し | コマンド | → `out/video.mp4` | |
| 9 | 報告 | Claude | → `report.md`（メモとの食い違い、単純化した点、自己検証で直した点、未解決の懸念） | **Gate3 動画**（常に人が見る） |

- 既定（`--review` なし）は 0〜9 を止まらずに実行する。Gate1・Gate2 では Claude が §9 のチェックリストで自己判定する
- 完成後の修正指示（「ここの動きを遅く」「この文を短く」など）は、該当ステップから再実行する。ステップ 5 以降は自動で追従する
- メモの内容に誤りが見つかった場合、台本は正しい内容で作り、`report.md` の冒頭で指摘する。裏取りできない主張は使わない
- 承認は各ファイル先頭の `status:` で記録する（`auto` = Claude の自己判定、`approved` = 人の承認）

### 2.1 学習メモの形式
- 自由形式の Markdown。見出し・箇条書き・コード・図の説明など何でもよい
- 任意の front matter で指示を与えられる
```markdown
---
point: B+木だと数段で見つかる、を伝えたい   # 伝えたい一点を指定（省略時は Claude が選ぶ）
audience: SQL を書いたことがある人          # 想定視聴者
---
```
- 1 つのメモに論点が複数あれば、動画化するのは 1 つ。残りは topic.md の「選ばなかった論点」に記録する

## 3. ファイル仕様

### 3.1 topic.md
id・題名・分野は `clip.yaml` に持つ（04 契約書 §2.1）。ここには重ねて書かない。
台本を書く前に「何のための技術か」「何がいちばん大事か」を決めておく設計書。台本はここから外れない。
```markdown
---
status: draft           # draft | auto | approved
---
# インデックスはなぜ速い？
## 生まれた理由
- 以前の状況：（その技術が無いと、どうしていたか）
- 困りごと：（それで何が困るか。具体的な数で）
- 発想：（それをどう解いたか。一言で）
## ゴール
（見終わった人が言えるようになる一文。例：「インデックスは、探す範囲を木で絞るから、行が増えても数段で見つかる」）
## 要点の地図
- 核：（ゴールを支える仕組みの一点。1 つだけ）
- 支え：（核を理解するのに要る事実。2〜3 個まで）
- 捨てる：（正しいが今回は言わないこと）
## 想定視聴者・前提知識
## パートの割り振り
- 前提（intro）：生まれた理由（以前の状況 → 困りごと）
- 本編（main）：発想 → 核の仕組み → 支え
- まとめ（outro）：ゴールの一文を言い直す
## 使いたい見せ方のアイデア
## 触れないこと（スコープ外）
```
- 「核」はゴールの一文に直接つながるものを 1 つ。核が 2 つ以上あると感じたら、論点が大きすぎる（片方を「選ばなかった論点」へ）
- 「捨てる」を空にしない。言わないことを決めると、残った情報に強弱が付く

### 3.2 research.md
- 主張ごとに出典を付ける：`[^1]` 形式の脚注。書籍は書名と章、Web は URL とアクセス日
- 出典の優先順位：公式ドキュメント（PostgreSQL / MySQL など）＞教科書＞信頼できる技術記事
- 「生まれた理由」（以前の状況・困りごと）にも出典を付ける
- 末尾に「動画で単純化する点と、その正当性」の節を必ず置く（嘘にならない範囲で省略しているかを確認するため）

### 3.3 script.md
- front matter に `status`, `chars`（ナレーションの総文字数。印は数えない）
- 見出しはパートごと：`## 前提（intro）` / `## 本編（main）` / `## まとめ（outro）`。`clip.yaml` の `parts` と同じ並び
- ナレーション文と、`> 映像:` で始まる映像指示を交互に書く
- ナレーション文の頭に重要度の印を付ける：`[核]` `[支え]` `[つなぎ]`。印は台本だけのもので、beats.yaml には写さない

```markdown
## 前提（intro）
[つなぎ] 1億行のテーブルから、1行を探す。
> 映像: …
[支え] 上から順に調べると、1億回の比較が要ります。
> 映像: …
## 本編（main）
[核] **インデックス**は、探す範囲を木で絞り込みます。
…
## まとめ（outro）
[核] 範囲を木で絞るから、行が増えても数段で見つかる。
```

文の規則：
- **問題から入る。** 前提パートは「その技術が無かったら何に困るか」を具体的な数や場面で見せてから、本編へ渡す。技術の名前から入らない
- **核にも支えにもつながらない文は書かない。** `[つなぎ]` は次の文への橋渡しだけ。並べるだけの豆知識は「捨てる」へ
- **核は 2 回言う。** 本編で 1 回、まとめで言い直して 1 回。強調 `**語**` は核の語にだけ使う
- **本編は単体で通じる。** 前提パートの言葉・図を指して「さっきの」と言わない（04 契約書 §2.2）。本編の最初の文で、何の話かを言い直す
- **略語は表記の規則（§3.9）に従う**

尺の目安（話速 1.1 倍で 1 秒 ≒ 5.5 字）：
| パート | 目安 | 字数の目安 |
|---|---|---|
| 前提 | 10〜25 秒 | 55〜140 字 |
| 本編 | 30〜90 秒 | 165〜500 字 |
| まとめ | 5〜15 秒 | 25〜80 字 |
| 総尺 | 上限 180 秒（Shorts の上限） | |

60 秒に収めることは目標にしない。核の意味を落とさずに言える最短を選ぶ。

### 3.4 beats.yaml
パートごとに置く（パート形式は `parts/<id>/beats.yaml`、単一形式はクリップ直下。04 契約書 §2）。id・題名は `clip.yaml` に持つ。
```yaml
voice:
  provider: voicevox        # voicevox（aivis はスキーマ上の予約。tts は未実装でエラーにする）
  speaker: 3                # ずんだもん（ノーマル）。決定済み Q3
  speed: 1.1
  pitch: 0.0
  intonation: 1.0
timing:
  leadIn: 0.3               # 動画冒頭の無音（秒）
  gap: 0.25                 # ビート間の無音（既定値）
  tail: 1.0                 # 最後の無音（秒）
beats:
  - id: hook                # 英小文字・数字・ハイフン。クリップ内で一意
    text: 1億行のテーブルから、1行を探す。
    # 以下は任意
    yomi: 一億ぎょうのテーブルから、いちぎょうをさがす。   # 読み上げ用。省略時は text
    subtitle: 1億行から1行を探す           # 字幕用。省略時は text
    gap: 0.6                # このビート後の無音を個別指定
    silence: 1.5            # 音声なしで映像だけ見せるビート（text は字幕のみ）
```
- `text` 中の `**語**` は字幕で強調色（黄）になる。読み上げ時は記号を除去する

### 3.5 読み辞書 `dict.yaml`
共通は `factory/dict.yaml`、クリップ固有は `clip/NNN-slug/dict.yaml`（任意）。
```yaml
B+木: ビープラスぎ
SQL: エスキューエル
PostgreSQL: ポストグレスキューエル
O(log n): オーダー ログ エヌ
```
- beats の `yomi` があれば、それをそのまま読む（辞書は適用しない）
- `yomi` がなければ `text` に辞書を適用する。共通とクリップ固有を合わせ（同じ語はクリップ固有が優先）、長い語から順に 1 回の走査で置換する（置換結果を再び置換しない）
- どちらの場合も強調記号 `**` は取り除く
- `yomi` がないときは、略語の直後の正式名称の括弧（`DNS（Domain Name System）` の `（Domain Name System）`。§3.9）も読み上げから取り除く。字幕には残る

### 3.6 timing.json（自動生成。手で編集しない）
パートごとに置く。フレームはパートの頭を 0 として数える。
```json
{
  "fps": 30,
  "durationInFrames": 1780,
  "sourceHash": "sha256（beats.yaml + factory/dict.yaml + クリップの dict.yaml）",
  "beats": [
    {
      "id": "hook",
      "startFrame": 9,
      "audioFrames": 84,
      "endFrame": 101,
      "audio": "audio/hook.wav",
      "subtitles": [{ "text": "1億行から1行を探す", "startFrame": 9, "endFrame": 101 }]
    }
  ]
}
```
- `endFrame` は音声のあとの gap を含み、次のビートの `startFrame` と一致する。silence ビートは `audio` を持たない
- 字幕は句読点で区切って 28 字以内のまとまりにし、文字数に比例した長さで音声区間に割り当てる（最後の字幕はビートの終わりまで）

### 3.7 report.md
- 冒頭：メモとの食い違い・誤りの指摘（なければ「なし」）
- 動画で単純化した点
- 自己検証で見つけて直した点、残っている懸念
- 主要フレームの静止画へのリンク（`clip/NNN-slug/stills/*.png`）

### 3.8 clip.yaml
形式と必須項目は 04 契約書 §2.1。ステップ 0 で Claude が生成する。新しいクリップは `parts` に intro / main / outro を書く。

### 3.9 表記の規則
- **略語は、各パートで初めて出るときに `略語（正式名称）` と書く。** 例：`DNS（Domain Name System）`、`CPU（Central Processing Unit）`。2 回目からは略語だけ。パートごとに数えるのは、本編パートが総集編で単体で使われるため
  - 読み上げは略語だけ（括弧は自動で読まない。§3.5）。字幕と、図の中に略語を書くときも同じ規則
  - 正式名称が日本語のほうが通じるときは日本語でよい：`TLB（アドレス変換のキャッシュ）`
  - 対象：英大文字 2 字以上の語（`DNS`、`TCP/IP`、`B+` は対象外）。`pnpm check` が字幕の初出を検査する（warn）
- 専門用語（略語でない語）も、初出で一言の言い換えを添える：「ハッシュ関数（キーを番号に変える計算）」
- 数・英語・記号の読みは `yomi:` か辞書で指定する（§3.4, §3.5）

## 4. コマンド仕様
コマンドは pnpm のスクリプトで、リポジトリのルートでも `factory/` でも同じように動く（ルートの `package.json` が factory に委譲する）。環境は Nix（`direnv allow` か `nix develop -c pnpm …`）。`001` は `clip/001-*` に解決される（パス指定も可。パスは `factory/` からの相対）。factory が読み書きするのは指定したクリップのディレクトリの中だけ（境界は 04 契約書）。

| コマンド | 動作 |
|---|---|
| `/make-video <クリップのパス> [--review]` | Claude Code のスキル（リポジトリのルートで実行）。メモから MP4 まで一気通貫で実行する（§2） |
| `pnpm studio` | Remotion Studio を起動し、全クリップをプレビューできる |
| `pnpm tts 001 [パート id]` | パートごとに beats.yaml から音声と timing.json を生成する。パートを省くと全パート。変更がないビートはキャッシュ（`audio/.cache/`）を使う |
| `pnpm check [001] [--strict]` | 検証する（下記）。クリップを省くと全クリップ。エラーがあれば終了コード 1 |
| `pnpm stills 001 [フレーム,…]` | 各ビートの始まり直後・中ほど・終わり直前と最終フレームを `stills/<フレーム>-<パート>-<ビート>.png` に書き出す（自己検証用。フレームはクリップ全体で数える。単一形式は `<フレーム>-<ビート>.png`）。フレームの指定もできる |
| `pnpm render 001` | check → レンダリング（`out/raw.mp4`）→ ラウドネス正規化 → `clip/001-db-index/out/video.mp4` |
| `pnpm voice-samples` | 話者の聞き比べ用 wav を `factory/.cache/voice-samples/` に作る |
| `docker compose -f factory/docker-compose.yml up -d` | VOICEVOX Engine を Docker で起動する（`127.0.0.1:50021`） |

### check の検証項目
`pnpm check` は gen-clips（全クリップの clip.yaml の検査と Composition 一覧の生成）と tsc（factory と clip の型検査）のあとに、次を検査する。
- 必須ファイル（契約書 §2）が揃っている。台本まわりの文書（memo / topic / research / script / report）が無いのは警告（`--strict` でエラー）
- clip.yaml の id・title・category・kit・parts（契約書 §2.1, §5）
- 以下はパートごと：
  - beats.yaml が §3.4 の形式に合い、ビート ID が重複しない
  - timing.json のビートが beats.yaml と一致し、`sourceHash` が最新である（古ければ tts の再実行を促す）
  - ビートの区間が連続し、音声より短くない。音声ファイルがある。字幕の区間がビートの中にある
  - どのビートからも使われていない `audio/*.wav` を警告する
  - Scene.tsx に `export default` があり、`useBeat("…")` のビート ID がすべてそのパートの beats.yaml に存在する
  - 略語の初出に正式名称の括弧が無ければ警告する（§3.9）
  - パートの尺が §3.3 の目安から外れたら警告する（単一形式は対象外）
- 総尺が 180 秒を超えたらエラーにする
- import の境界と factory 側の直書き（契約書 §6）
- 将来：各ファイルの `status` の検査（`--review` 時は approved を要求）。今は Claude がスキルの手順で確認する

|---|---|
| エンジン | VOICEVOX Engine（HTTP, localhost:50021） |
| 話者 | ずんだもん（ノーマル、speaker 3）。決定済み Q3。クリップごとに beats.yaml で変更できる。動画に「VOICEVOX:ずんだもん」のクレジットを表記する |

## 6. 字幕仕様
| 項目 | 値 |
|---|---|
| 位置 | 字幕領域（x = 60〜900, y = 1390〜1536）の中央。下部 UI（y > 1536）と右端のボタン列（x > 900）を避ける（§7.3） |
| フォント | Noto Sans JP Bold, 56px（行間 1.3）, 白（`theme.text`）, 縁取りなし・薄い影（`0 2px 8px`） |
| 1 枚の上限 | 28 字（1 行 14 字 × 最大 2 行。幅 840px に 56px で 15 字入る）。超える場合は句読点で分割し、文字数に比例した時間で切り替える |
| 改行 | 文節単位（`Intl.Segmenter("ja")` で単語に分け、助詞・句読点を直前の語に結合して、文節の途中では折り返さない） |
| 強調 | `**語**` を黄色（`#F4D35E`）で表示 |
| 表示切り替え | フェードなしで切り替える |

## 7. 映像仕様
| 項目 | 値 |
|---|---|
| 解像度 / fps | 1080×1920 / 30fps |
| 背景 | 単色 `#0E1116` |
| メイン領域 | x = 60〜960, y = 240〜1350 |
| 最小文字サイズ | 40px（図中のラベルを含む） |
| タイトル表示 | 最初のパート（前提）の冒頭で大きく出し、以降は表示しない（決定済み Q4）。タイトルを持つのは `clip.yaml` の `title`。本編パートはタイトルを出さない（総集編で使い回すため） |
| パートの境目 | 前のパートの最後 0.3 秒で消え、次のパートの最初 0.3 秒で現れる（`Clip.tsx` が共通で行う。クリップの最初と最後は除く）。消える・現れる間は無音になるよう、最後以外のパートは beats.yaml の `timing.tail` を 0.5 秒前後にする |
| 終端 | 最後の 1 秒は最終状態で静止する（ループ再生時のつなぎ） |
| クレジット | 最後の約 1.5 秒に「VOICEVOX:ずんだもん」を画面下部に表示する（`Clip.tsx` が共通で描く。Scene は関与しない） |

以下 §7.1〜7.6 は見た目の規約。`/review-video` の採点基準でもある（数値を直したらスキルも直す）。

### 7.1 色の役割
色は `theme` の名前で使い、1 本の中で同じ色を別の意味に使わない。
| 色 | 役割 | 例 |
|---|---|---|
| text | 主役の文字・図の線 | 値、ラベル |
| muted | 文脈・処理済み・補助。不透明度 0.15〜0.4 で使うことが多い | 暗くした箱、構造線 |
| yellow | 「今見てほしい 1 点」。同時に 1 か所だけ（字幕の強調語と同じ） | 注目中の箱 |
| blue | 対象。探している物・調べている範囲 | 検索キー、候補範囲 |
| green | 成功・正解・結果 | 見つかった、速い |
| red | 失敗・不要・遅い・警告 | 全件走査、衝突 |

text / muted を除き、同時に画面にある色は 4 色まで。意味のない装飾色は使わない。

### 7.2 余白と図の占有
- 図の外接矩形（図ボックス）の中心は、メイン領域の中心（x 510 / y 795）から ±60px 以内に置く。左右どちらかに寄せない
- 図ボックスはメイン領域の高さの 55% 以上（610px）、幅の 70% 以上（630px）を占める。小さい図は拡大するか、式・結果を足して領域を使う
- 上下の余白の差は 25% 以内。余白が片側に溜まるときは図を動かす
- 図の端は x60 / x960 から 20px 以上内側、字幕領域から 40px 以上離す

### 7.3 プラットフォーム UI の避け方（Shorts / TikTok）
- 下部約 20%（y 1536〜1920）と右端（x 900〜1080 の y 960〜1700）は投稿者名・説明・ボタンで隠れる。重要な文字・図・字幕をここに置かない
- 上端（y 0〜180）も隠れる。タイトルはメイン領域内に置く
- クレジット（最後の約 1.5 秒）は例外として下部に置いてよいが、x < 900 に収める
- 字幕領域（§6）は x 60〜900, y 1390〜1536 で、危険域に入らない。図は字幕領域から 40px 以上離す（メイン領域の下端 y1350 と字幕上端 y1390 が 40px）

### 7.4 強調の作法
- 強調は同時に 1 つ。強調中、ほかは不透明度 0.4 以下に暗くする（消さない）
- 強調の手段は 1 場面につき 1 種類（色・拡大・輪郭のどれか）に統一する
- 新しい概念は、図を先に見せ、式や用語は後から足す
- ラベルは対象の隣に付ける。離れるときは矢印で結ぶ
- 値は具体的な数にする（「n」より「15」）

### 7.5 イージングと間
- 登場・移動は ease-out（初速が出て減速する）。ease-in は初動が遅く見えるので使わない。常に動く物だけ linear
- 1 つの動きは 0.3〜0.6 秒。0.2 秒未満はぎこちなく、0.8 秒超は説明では冗長
- 登場は 0.92〜0.95 倍＋不透明度 0 から始める。0 倍から広げない
- 動きの間に 0.2〜0.4 秒の静止を置く。字幕が切り替わる直前は動きを止める
- 動かす理由（注意の誘導・状態変化の説明・空間の連続性）を言えない動きは入れない

### 7.6 密度
- 場面の骨格となる図は残し、追加物はその周りに足す。同時に画面にある意味のある物は 4〜5 個まで
- 序盤は疎に、結論に向けて密にする

## 9. ゲートのチェックリスト
自動実行時は Claude がこのリストで自己判定し、結果を report.md に残す。
- **Gate1（論点）**：「生まれた理由」（以前の状況・困りごと・発想）が具体的に書けているか / ゴールは一文で、見終わった人が言える形か / 核は 1 つで、支えは 3 個以内か / 「捨てる」が空でないか / 動きで見せる価値があるか（静止画で足りる話ではないか）
- **Gate2（台本）**：
  - 筋：前提パートが困りごとから入り、技術の名前から入っていないか / 本編が「発想 → 核 → 支え」の順で、ゴールに向かっているか / まとめがゴールの一文を言い直しているか
  - 強弱：全ナレーションに `[核]` `[支え]` `[つなぎ]` の印があり、どこにもつながらない文が無いか / 核が本編とまとめで 2 回言われ、強調 `**` が核の語だけか
  - 表記：略語の初出が `略語（正式名称）` か、専門用語の初出に言い換えがあるか（§3.9）
  - 単体性：本編が前提パートを指す言葉（「さっきの」など）を使わず、単体で通じるか
  - 正確さ：主張に出典があるか / 単純化しすぎて嘘になっていないか
  - 尺：各パートが §3.3 の目安に収まり、総尺が 180 秒以内か。最初の 3 秒（前提パートの冒頭）で問いか困りごとが出ているか
- **Gate3（動画）**：一度に動いているものは 1 つか / 字幕を読む時間は足りるか / セーフエリア内か / 音なしでも理解できるか。観点ごとの 0〜2 点の採点は `/review-video` に従い、`report.md` に残す
